Date : 2026-11-08

Méthode : revue de code manuelle ciblée (OWASP Top 10), greps systématiques, exécution de la suite de tests, PHPStan, `composer audit`.

## Points forts confirmés

### Injection SQL
- Requêtes préparées partout ; `PDO::ATTR_EMULATE_PREPARES => false`.
- Les seules interpolations dynamiques (ORDER BY, colonnes de comptage,
  noms de tables du dumper) passent par des listes blanches ou des regex
  strictes (`AbstractManager::buildOrderClause`, `buildWhereClause`,
  `assertValidColumnNames`, `EquipementManager::compterPar`).
- Pagination bornée (fix #83 vérifié dans `JournalManager`).

### XSS
- Auto-échappement Twig ; seulement 5 usages de `|raw`, tous justifiés
  (contenu Parsedown en `setSafeMode(true)`, valeurs `json_encode`
  dans des scripts à nonce).
- CSP stricte sans `unsafe-inline` : `script-src 'self' 'nonce-…'
  https://cdn.jsdelivr.net`, `object-src 'none'`, `base-uri 'self'`,
  `form-action 'self'`, `frame-ancestors 'self'`.
- `TemplatesCspTest` impose l'absence d'attributs `onclick=` etc.

### CSRF
- Jeton de session vérifié par `hash_equals` sur toutes les actions
  POST (22 contrôleurs couverts), y compris login et reset de mot de
  passe ; régénération après login et après échec.

### Authentification et session
- bcrypt (`PASSWORD_DEFAULT`), hash factice anti-énumération temporelle,
  limitation des tentatives (5/identifiant, 30/IP), TOTP RFC 6238 +
  passkeys WebAuthn, codes de secours hashés.
- Cookie : HttpOnly, SameSite=Lax, Secure en HTTPS, `use_strict_mode`,
  régénération d'ID à la connexion/déconnexion, durée 15 min.
- Re-synchronisation du rôle à chaque requête ; compte supprimé =
  session fermée (S5). Champs sensibles exclus de la session (P34).

### Réinitialisation de mot de passe
- Jeton stocké **haché** en base (`empreinteJetonReset`), expiration,
  anti-énumération (réponse identique), quota par IP et par compte.

### Uploads et fichiers
- Images : liste blanche MIME finfo, décodage GD + réencodage WebP/JPEG
  (les polyglottes PHP/HTML sont détruits), plafond de pixels, nom
  généré serveur. `public/images/.htaccess` interdit tout script/HTML/SVG.
- Factures : MIME restreint (PDF/JPG/PNG), 10 Mo max, stockage hors
  docroot (`_storage/`), service par `UploadController` avec garde
  `realpath` anti-traversée et `deniAccessUnlessGranted('ROLE_USER')`.

### Mise à jour et sauvegardes
- Archive : SHA-256 vérifié (`hash_equals`), entrées zip validées avant
  extraction (anti zip-slip C1), vendor exigé, dump SQL avant migration,
  restauration de vendor en cas d'échec.
- Sauvegardes : manifeste signé par HMAC dérivé de `SECRET_KEY`,
  empreinte de clé dans le manifeste, liste blanche d'entrées.
- Réservé à `ROLE_SUPER_ADMIN`.

### Configuration et infrastructure
- `.htaccess` racine « Require all denied » (docroot = `public/`
  uniquement) ; `setup/` interdit + 403 après installation.
- `.env.local.php` gitignored, mode 600, jamais réécrit par le processus
  web ; secrets absents des sauvegardes.
- Chiffrement applicatif AES-256-GCM (clé HKDF, AAD), déchiffrement
  legacy CBC maintenu.
- Erreurs : log serveur uniquement, jamais de stack trace côté client.

## Risques résiduels et recommandations

### R1 — Ancre de confiance de la mise à jour (moyen/faible)
L'archive **et** sa somme SHA-256 proviennent de la même release GitHub,
via HTTPS. La somme ne protège que contre la corruption/erreur, pas
contre un compte GitHub ou un dépôt compromis : un attaquant qui publie
une release malveillante fournit aussi la somme correspondante.
*Recommandation :* signer les releases (GPG ou minisign, clé publique
embarquée dans l'application) ou épingler la somme d'un canal
indépendant.

### R2 — Déploiement derrière un reverse proxy (moyen/faible)
`public/index.php` détecte HTTPS via `$_SERVER['HTTPS']`/`SERVER_PORT`
et lit l'IP client directement ; `Request::setTrustedProxies()` n'est
jamais appelé. Derrière un proxy terminant TLS :
- `cookie_secure` et HSTS peuvent ne pas s'activer ;
- `getClientIp()` voit l'IP du proxy : le throttling par IP (30 échecs)
  devient commun à tous les utilisateurs (blocages croisés) ou
  contournable via `X-Forwarded-For` non filtré.
*Recommandation :* documenter (ou configurer via `.env.local.php`)
`setTrustedProxies(['IP_DU_PROXY'], Request::HEADER_X_FORWARDED_FOR |
Request::HEADER_X_FORWARDED_PROTO)`.

### R3 — CDN sans SRI (faible)
`templates/_layout.twig` charge Bootstrap 5.3.8 depuis
`cdn.jsdelivr.net` **sans attribut `integrity`**. La CSP autorise ce
domaine : une compromission du CDN injecterait du JS dans toutes les
pages.
*Recommandation :* ajouter `integrity="sha384-…"` + `crossorigin`,
ou héberger les assets en local (simplifierait aussi la CSP).

### R4 — Limiteur de connexion « fail-open » (faible)
Si la table `login_throttle` est indisponible (migration non jouée),
la connexion reste possible sans limitation — choix documenté et
journalisé, mais à connaître : une indisponibilité prolongée rouvre
la voie au brute-force.
*Recommandation :* alerte/monitoring sur le message de log
`[AppUserAuthenticator] Limiteur de tentatives indisponible`.

### R5 — Coût bcrypt par défaut (faible)
`PASSWORD_DEFAULT` = bcrypt coût 10 (PHP 8.4). Coût 12 reste très
confortable côté serveur et double le travail d'une attaque hors ligne.
*Recommandation :* `password_hash($p, PASSWORD_BCRYPT, ['cost' => 12])`
aux 5 points de hashage, migration transparente au prochain login.

### R6 — Prérequis MySQL ≥ 5.7 (hygiène)
MySQL 5.7 est en fin de vie (oct. 2023). Le code n'utilise rien de
spécifique 5.7 ; recommander MySQL 8.0+/MariaDB 10.6+ dans le README.

### R7 — Durée de vie de session côté serveur (très faible)
L'expiration 15 min est appliquée applicativement
(`getLastUsed()` + `invalidate()`), mais `session.gc_maxlifetime`
n'est pas fixé : selon le `php.ini` de l'hébergeur, les fichiers de
session peuvent être purgés trop tôt (déconnexions intempestives) ou
s'accumuler.
*Recommandation :* passer `gc_maxlifetime` explicitement à
`NativeSessionStorage`.
